\chapter{Project Background and Objectives}

VERAIO is a set of utility codes used to provide a common set of input and outputs to the \ac{vera}.
\ac{vera} is a collection of several different computer codes and having a common input and output,
instead of having to deal with input and output from each individual code, allows VERA to be easy to use
and reduces errors associated with code operability.
The VERAIO utilities include VERAIn, VERAView, and VERARun. Each of these utilities is described below.

VERAIn is an input processor that reads an ASCII input file generated by users, parses the file,
performs some error checking, and writes an XML file that is intended to be read by other VERA codes.
The main purpose of VERAIn is to provide a common input to all of the VERA codes so users only have
to learn one input.   VERAIn is written in Perl and uses YAML configuration files to provide flexibility.

VERAView is a \ac{gui} that reads a VERA HDF output file and allows users to visualize results.
VERAView is written in Python.

VERARun is a script that drives the VERA execution in a \ac{hpc} environment.

Work performed at the code-level supports the {\it VERA-QA-001, \ac{qapp}} and {\it VERA-QA-002, VERA Software Quality Assurance Plan}.

\chapter{Definitions and Acronyms}

The following defines terms used in this Plan.
Acronyms are defined with their first use in this Plan.
Defined terms and document titles are annotated in this Plan by Italics.
Plan section or appendix titles are annotated by quotation marks.

\begin{description}
\item{Baseline: A specification or product that has been formally reviewed and agreed upon, that thereafter serves as the basis for the use and further development, and that can be changed only by using an approved change control process.  Source: ASME NQA-1a-2009}
\item{Branch: Also referred to as topic branch.  Refers to a branch in the VERAIO Git repository that is not the master branch.  More information can be found at \url{https://guides.github.com}.}
\item{Code repository: Also referred to as VERAIO repository, VERAIO code repository, and simply repository.  The code repository stores all source code, tests, configuration instructions, and documentation.  Version control is performed using the Git version control system (see \url{https://guides.github.com}).}
\item{Commit: A specific configuration of the code repository that is identified by a unique \ac{sha} number.  See \url{https://guides.github.com} for more information.}
\item{Gitlab: Internal ORNL and UM website for hosting the VERAIO code repository, running automated continuous integration tests, and submitting and performing merge request reviews.  See \url{https://about.gitlab.com} for more information.}
\item{TRAC: System for tracking activities and issues related to VERAIO development work.  Activities and issues are tracked using tickets through all stages of development, including planning, development and review.  After tickets are closed, they are archived indefinitely.
TRAC also refers to the website managed by \ac{phi} Infrastructure where tickets are entered and edited.}
\item{Merge request: A request to merge new code changes into the baseline version of the code.  A merge request is submitted by the developer to an independent reviewer who must approve changes before they can be merged.  Additionally, the new changeset must pass all automated tests prior to their merge.}
\end{description}

\section{Organization}

Each VERAIO code team member shall adhere to this Plan.
The VERAIO \ac{psm} retains overall responsibility for ensuring adherence to this Plan.
High level VERA Product Suite design requirements are made at the VERA leadership level and flow down to the VERA \acp{psm} in the form of individual code requirements.
VERAIO code development, review and testing is conducted by a small group of VERAIO Code Developers and Independent Reviewers as supervised by the \ac{psm}.
After approval at the code-level, additional reviews and tests are conducted at the VERA Product Suite level under processes defined in the VERA \ac{sqap}.

\chapter{Software Risk Management}

The Software Risk Management described in {\it VERA-QA-002, VERA Software Quality Assurance Plan}, have been reviewed.

The software work activities implemented by the code team will ensure the software meets its intended function before release to the nuclear industry.

\section{Software Quality Level}

VERAIO has been determined to be SQL2 based on the fact that VERAIO will be used for supporting nuclear reactor safety analysis.
This plan defines how the following software specific work activities will be implemented for the VERAIO product:
\begin{enumerate}
\item Configuration Management
\item Software Acquisition
\item Software Requirements
\item Software Design
\item Software Verification and Validation
\item Software Problem Reporting and Corrective Action
\item Training
\end{enumerate}

\section{Risk Management}

Software risk management, which includes software failure analysis, provides a disciplined environment for proactive decision making to continuously assess what can go wrong, determine what risks are important to address, and implement actions to address those risks.
VERAIO is in the maintenance phase of the development life cycle, which requires frequent changes to support the next VERA Product Suite software release.
The \ac{psm} is responsible for managing identified code-level risks that would potentially impact the successful completion of the next VERA Product Suite software release:

\begin{description}
\item Introduction of code defects: Mitigating factors include software design and in-process code reviews, training and qualification of code developers, and PSM mentoring and oversight
\item Inadequate resources for completing of software requirements implementation: Mitigating factors include the establishment of technical and resource-loaded performance parameters and milestones that are tracked and correlated with cost and schedule data
\end{description}

\section{Software Design}

Software design follows \VERAReq.
VERAIO does not have a single design document.
Code design for code changes is discussed in TRAC tickets.
TRAC tickets must be reviewed by an Independent Reviewer before closing.
Closed TRAC tickets are archived indefinitely.
See the ``Software Design Review'' section of this Plan for additional information on design reviews.
% Code models and numerical solution are discussed in the VERAIO Theory Manual.
A high level overview of code organization is given in the Programmer's Manuals.

Design traceability is maintained by adding a TRAC ticket number to code changes and merge requests, which describes motivation, design, and testing related to the code changes.

\section{Software Implementation and Control of Libraries}

VERAIO software is implemented as outlined in the ``Configuration Change Control'' section of this Plan using designated VERAIO coding practices.
Third-party code (functional libraries, such as solvers) and data (non-functional) libraries are utilized by VERAIO and are obtained from the VERA development environment.
Regardless of type, all libraries are managed and controlled by the  \ac{phi} Infrastructure Team.
VERAIO libraries are included on the Support Software and Libraries Software Configuration Item List.
See the ``Coding Standards, Practices, and Conventions'' section of this Plan for additional information.

\section{Software Testing}

Testing is planned and conducted in accordance with \VERAReq\ and {\it VERA-QA-009, VERA Release Process}.

\section{Code Availability for VERA Product Suite Integration}

The master branch of the VERAIO Gitlab site is always available for VERA Product Suite integration.
The master branch is synced to the casl-dev repository on a nightly basis using an automated sync script.
The sync script performs VERA Product Suite level automated casl-dev system testing prior to syncing the VERAIO Gitlab site with the casl-dev repository.
VERA Product Suite releases are made from the casl-dev repositories.

\section{Security, Backup, and Recovery}

Code access is controlled through the VERAIO Gitlab site.
Access must be explicitly granted on a per-user basis by the \ac{psm}.
Code backup and recovery services are managed by the ORNL Information Technology Services.
